## 2. 手動での確認（合成の値。利用者の端末）

```bash
TREBUCHET_DATA_DIR="$PWD/.tmp/quickstart-006" pnpm dev    # http://localhost:5173
```

パスキーの登録の後、合成の事業体を作り、補助科目（銀行 1、カード 2）を作る。

1. **貼り付け（US1）**: 「明細」→「貼り付けて取り込む」に `packages/domain/test/fixtures/mfme/paste-basic.txt` の中身を貼り、年を選ぶ → プレビューに件数・期間・入出金の合計・読めない行（合計の行）が出る。未対応の口座があると取り込めない → 各口座の用途と科目を選ぶ → 取り込む。同じ内容をもう一度貼ると新規 0 件
2. **候補と承認（US2）**: 未処理の一覧で候補・判定・確信度・根拠が出る。1 件を直して承認 → 仕訳帳に出所「明細」の仕訳。1 件を2行に分け、合計が合わないと承認できない。私用の口座の事業の経費が 事業主借 で登録される。私用の口座の私用の明細を除外 → 帳簿に出ない → 除外の取消で未処理に戻る
3. **既存の仕訳（US2-10）**: 定期仕訳（005）で家賃を登録した月の銀行の出金が「既存の仕訳と結びつける」候補になり、承認しても仕訳が増えない
4. **取消（US2-9）**: 明細から登録した仕訳を仕訳の詳細から取り消す → 明細が未処理に戻る。訂正では登録済みのまま
5. **ルール（US3）**: 同じ内容の明細の2件目以降が「ルール」の候補になる。候補と違う科目で承認するとルールが変わり、履歴が残る。ルールを止めると候補に使われない
6. **まとめて承認（US2-7）**: しきい値以上の候補をまとめて承認。締めた年度の明細だけが理由つきで残る

## 3. 実データ・実環境での確認（利用者の端末。値は書かない）

1. **貼り付けの形（R2）**: MF ME の入出金の画面で表を選んでコピーし、§2.1 の手順で貼る。全行が読めるか、読めない行の理由が妥当かを確かめる。列の名前・金額の書式が R2 の想定と違えば、違いの**形**（列の名前・並び）だけを報告し、`paste.ts` とフィクスチャを直す
2. **端末内の AI（R10）**: `fm available` が使えると答えること。AI の設定で端末内を有効にし、ルールに一致しない明細で「AI で推定」→ 候補に「端末内の AI」と出る。`response_format` を付けた要求が通るかを server のログ（エラーの種類だけ）で確かめる
3. **外部の AI（R10・R11）**: 設定で接続先・モデル・API キーを入れて有効にし、端末内の確信度が低い明細だけが外部へ送られることを、server のデバッグの出力（送信の内容。マスクされていること）で確かめる。API キーが画面・ログ・データ場所に出ないこと
4. ~~**MF ME からの取得（US4, R13）**~~ 取りやめ（2026-10-26。T034 で削除）
5. **時間（SC-001, SC-006, SC-007）**: 1 か月分（約 100 件）の確認と登録が 15 分以内か、500 件の貼り付けから候補の一覧まで 5 秒以内か、取得が認証を除いて 3 分以内かを計る
6. **精度（SC-004, US5）**: 前年の明細を登録した後、当年 1 月 1 日を基準日に評価を実行し、科目と判定の一致率が 80% 以上かを見る（率だけを控える）
