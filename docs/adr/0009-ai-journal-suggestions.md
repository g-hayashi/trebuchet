# ADR 0009: AI による仕訳の推定は、ルール → 端末内 → 外部の順に、マスクした情報だけを送り、人が承認してから登録する

- 状態: 採用
- 日付: 2026-10-26
- 関連: specs/006-mfme-ai-journal/research.md R8, R10, R11, R12, R13, R17、ADR 0007

## 状況

MF ME の明細（貼り付け。Playwright による取得は取りやめた）から仕訳の候補を作る。ルールで決まらない明細は AI に推定させたい。一方で、明細には口座・カードの番号、振込の名義、メモなどの個人情報が混じり、AI の出力は誤ることがある。AI を呼ぶのは遅く、外部の API には情報が出る。

## 決定

- **推定の順序は 既存の仕訳 → 振替の対 → ルール → 端末内の AI → 外部の AI**（R8）。前の段で候補ができれば後の段を呼ばない。端末内の確信度が `external_threshold`（既定 60）より低く、外部が有効なら外部を呼ぶ。端末内を呼べないときは、外部が有効ならルールに一致しない明細を外部へ送る。どの段でも作れなければ `none`
- **OpenAI 互換の Chat Completions で呼ぶ**（R10）。端末内は macOS の `fm serve`（モデル名 `system`、`stream` は送らず SSE を読む、`127.0.0.1`、ポート `TREBUCHET_FM_PORT` 既定 18790）を最初の推定で子プロセスとして起動し、server の終了で止める。外部は接続先の URL・モデルを端末の設定、API キーをキーチェーン（004 と同じ `SecretStore`）に置く。依存は足さず `fetch` で呼ぶ
- **AI の出力は `AiSuggestion`（Zod）で検証する**。形に合わない出力、一覧にない科目のコード、未知の税区分は捨てて「候補なし」にする（INV-46）。取引先は AI に推定させない
- **送る情報は `buildAiPayload` を通したものだけ**（R11、INV-45）。許可した項目（日付、金額、向き、マスクした内容、MF ME の大項目・中項目、口座の種類と用途）から組み立てる。口座の名前・メモ・明細の ID・取引先の一覧は送らない。端末内にも外部にも、評価にも同じ形を送る（`createAiSuggester` を共有）
- **マスク `maskContent`**: 4 桁以上の数字の並び → `####`、メールアドレス・電話番号の形 → `[連絡先]`、内容が振込・振替で始まるときはその後ろ（名義）→ `[名義]`
- **AI の呼び出しはトランザクションの外**。`inferWithAi` は 読む → AI を呼ぶ → 書く の 3 段。候補は `statement_candidates` に保存し、AI を何度も呼び直さない。取込と承認は 1 つの UnitOfWork で書く（INV-47）
- **承認だけが仕訳を作る**（INV-41）。AI の候補は提案で、利用者が確かめて承認する。確信度が高い候補のまとめて承認（`bulk_threshold` 既定 80）も、利用者の操作である
- **AI の接続の設定は端末のもの**（R12）。registry の `ai_settings` に置き、バックアップに含めない。しきい値は事業体の `statement_settings`
- **評価**（R17）。登録済みの明細を正解に、基準日より前のルールで基準日以後を推定して一致率を `eval_runs` に保存し、前回と比べる。AI を含めるかは実行のときに選ぶ。結果は帳簿の中に置き、リポジトリに書かない

## 理由

- 費用・速度・漏えいの危険の小さい順に試す。ルールと端末内で済めば、情報は端末から出ない
- `fm serve` が同じ形の API を出すので、呼び出しの実装が 1 つで済む。明細ごとに `fm` を起動するよりモデルの読み込みが 1 回で済む
- 送る項目を許可制にすると、後からフィールドが増えても自動では送られない。マスクの検査（INV-45）も 1 つの関数に集まる
- 検証と承認を挟めば、AI が誤っても帳簿は人の確認なしには変わらない。トランザクションの外で呼ぶので、遅い・失敗する呼び出しが書き込みを止めない

## 限界

- **マスクは口座名・メモ・4 桁以上の数字・振込の名義を除くが、利用名に混じる個人名は伏せきれない**。クレジットカードの利用名や店名に個人名が含まれる場合、それは内容に残り、外部の AI にも送られる。個人名を機械的に見分ける規則は誤りが多く、取引先の判定を壊すので採らない
- この限界のため、外部の AI は既定で無効にし、利用者が設定で有効にしたときだけ使う。端末内の AI だけを使えば、情報は端末から出ない
- `fm serve` が `response_format` を受けるかは実環境で確かめる。受けなくても出力の検証は同じ

## 検討した代替案

- 氏名をマスクする辞書や固有表現の抽出: 誤りが多く、店名や取引先を壊す。限界として明記する方を選んだ
- 明細をそのまま AI に送る: 憲法 III（口座番号・カード番号・個人の識別情報のマスク）に反する
- AI の呼び出しを UnitOfWork の中に入れる: 書き込みのロックを長く保ち、外部の障害で巻き戻しが起きる
- `fm respond` を明細ごとに起動する: モデルの読み込みが毎回かかる
- AI の呼び出しを domain のポートにせず server に置く: 推定の順序と候補の組み立てが domain の外に出る。呼び出しだけを `SuggestionProvider` のポートにした

## 影響

- テストは `fm`・外部の AI・Chromium を呼ばない（偽の `SuggestionProvider`・偽の `fetch`）
- 送る項目を増やすときは、`buildAiPayload` と INV-45 の性質テストを同時に直す
- （取りやめ 2026-10-26）MF ME の画面からの取得（Playwright）は利用者の判断でやめた。実装は削除済み。汎用の明細取込は 007 で作る。以下は当時の設計: 取得した行は貼り付けと同じ型にして同じプレビューへ渡す（R13）。画面のセレクターは `lib/mfme/dom.ts` の 1 か所に置く
