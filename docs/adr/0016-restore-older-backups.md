# ADR 0016: 古い版のバックアップを移行して復元し、起動時の移行の前に写しを取る

- 状態: 採用
- 日付: 2026-11-17
- 関連: [ADR 0007](0007-backup-format.md)（「版」の決定を置き換える）、[ADR 0011](0011-passkey-prf-vault.md)、004 FR-027

## 状況

2026-11-16 に公開し、利用者がいる。利用者は手元の帳簿とバックアップを持ったまま新しい版に更新する。ADR 0007 は、開発中で帳簿の形式を更新しない前提で、アプリの版（registry と tenant のマイグレーションの適用数）が完全に一致するバックアップだけを受け付けていた。この規則では、マイグレーションを 1 つ足した版に更新すると、それまでのバックアップがすべて復元できない。また、起動時は DB を開くたびにマイグレーションを当て、当てる前の DB を残していなかった。

## 決定

- **版の受け入れ**: registry と tenant の適用数がどちらも今以下なら受け付ける。どちらかが今より大きい（新しい版で作った）ものは `VERSION_MISMATCH` で拒否し、「アプリを更新してから復元してください」と示す。形式の版（`format`）の扱いは変えない
- **古い版の復元**: 仮の場所に展開し、暗号化した DB に今の版までのマイグレーションを当て、`integrity_check` を通してから、端末の設定を引き継いで入れ替える。途中で失敗したら元のデータ場所は変えない（`RESTORE_FAILED`）。入れ替えの後の初回の `migrate` に頼らない。復元先のデータ場所も古いことがある（更新の直後で server を起動していない）ので、復元の前の写しと端末の設定は、今のデータ場所を仮の場所に写して今の版まで当ててから読み、生きているデータ場所は改名まで変えない。今のデータ場所が今の版より新しければ失敗する
- **起動時の写し**: 既存の DB に未適用のマイグレーションがあるときだけ、当てる前に `VACUUM INTO` で暗号化のまま `<データ場所>/pre-migrate/` に写す。種類ごと（事業体は事業体ごと）に直近の 3 個を残す。写しに失敗したらマイグレーションを当てずに失敗する。未適用の判定は drizzle の migrator と同じ方法（`folderMillis` と `__drizzle_migrations.created_at` の最大）
- マイグレーションは足すだけにする（`docs/development.md` の「互換性」）。適用数の大小で版の新旧が決まるのはこの規則による

## 理由

- 利用者が更新のたびに過去のバックアップを失うのは、バックアップの目的に反する
- 移行を仮の場所で済ませれば、失敗しても今の帳簿は変わらない。既存の復元の「展開 → 検査 → 改名」に 1 段足すだけで済む
- 新しい版のデータを古いアプリで読むことは保証できない（列・制約を知らない）
- 起動時の写しは、バックアップを設定していない利用者も、更新の不具合から戻せるようにする

## 検討した代替案

- 版の一致を続け、古い版のアプリで復元してから更新する手順を案内する: 古い版のアプリを手元に用意させることになり、利用者の手間が大きい
- 入れ替えの後の初回の `migrate` に任せる: 移行に失敗したとき、元の帳簿はすでに改名で退いていて戻す手順が要る

## 影響

- 過去のリリースのバックアップを今の版で復元できることを、見本のバックアップで継続して確かめる（`packages/db/test/fixtures/backups/v<版>/` を `pnpm backup:fixture` で足し、`backup-fixtures.test.ts` が CI で全部を復元して照合する。手順は `docs/development.md` の「リリースの手順」）。`.tbk` のヘッダーに任意の項目 `release`（作ったアプリのリリースの版）を書き、拒否の文言に示す（判定はマイグレーションの数のまま）
- `pre-migrate/` の写しは事業体を消すときに一緒に消す
