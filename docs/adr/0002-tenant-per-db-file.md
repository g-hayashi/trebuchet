# ADR 0002: 事業体ごとに DB ファイルを分け、帳簿テーブルに entity_id を持たせない

- 状態: 採用
- 日付: 2026-10-18
- 関連: specs/001-ledger-core/research.md R9、data-model.md §0、.specify/memory/constitution.md III

## 状況

アプリは事業体（entity）ごとに帳簿を管理する。事業体のデータが混ざると、別の事業体の仕訳や残高を読んだり書いたりする事故になる。同じ DB の中で事業体を区別する方法（全テーブルに `entity_id` を持たせ、すべてのクエリに条件を付ける）では、条件の付け忘れを防ぐ仕組みがない。

## 決定

- 事業体ごとに SQLite ファイルを 1 つ作る: `data/tenants/<事業体ID>.sqlite`
- 帳簿のテーブル（仕訳、科目、期間など）に `entity_id` 列を持たせない
- 事業体の一覧だけを `data/registry.sqlite` に置く
- 1 回のリクエストで開くテナント DB は 1 つだけにする
- 同じマイグレーションを、すべてのテナント DB に適用する

## 理由

- 別の事業体のデータは、そもそも同じファイルにないため、SQL の条件漏れで読めない
- テナント DB に `entity_id` がないため、テーブル定義とクエリが単純になる
- ファイルが事業体ごとに分かれているため、事業体単位でのバックアップ、削除、移動がファイルの操作で済む
- Constitution III（テナントごとの DB ファイル分離）に従う

## 検討した代替案

- 1 つの DB に `entity_id` 列を持たせる: 全クエリに条件が必要になり、付け忘れを機械的に防げない。分離のテストも全クエリを対象にする必要がある

## 影響

- マイグレーションは、すべてのテナント DB に同じ内容を適用する
- テナントをまたぐ SQL は書けない。事業体をまたぐ処理が必要になったら、アプリ側で DB を 1 つずつ開いて集める
- 分離は次のテストで確認する: `apps/server/test/isolation.api.test.ts`、`packages/db/test/isolation.property.test.ts`
- 事業体の一覧は `registry.sqlite` が持つ。帳簿の内容は持たない
