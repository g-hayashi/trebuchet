> **008 での変更（2026-10-30）**: 暗号の鍵は、パスフレーズ + Argon2id から `HKDF-SHA256(DK, ヘッダーの salt, "trebuchet/backup/v1")` に替わった。ヘッダーには、取った時点の recovery の包み（`salt`・`iv`・`tag`・`wrapped`）が入り、回復キーだけで復元できる。パスフレーズ、キーチェーンへの保存（`/usr/bin/security`。`SecretStore` は 006 の外部の AI の API キーのために残る）、設定・変更の画面と API、「パスフレーズが使えない」の警告はなくなった。`pnpm restore` は回復キーを標準入力から読み、ヘッダーの包み → 今の `auth.sqlite` の包みの順に試す。復元の後は `auth.sqlite` を recovery の包みだけで作り直し、次の起動で回復キーで解錠してパスキーを登録する。定期実行は解錠中だけ。AES-256-GCM とヘッダー全体の AAD、スナップショット（`VACUUM INTO`）、世代、版の完全一致は、この ADR のまま。中の SQLite の写しは平文（外側の AES-GCM が守る）。詳細は [ADR 0011](0011-passkey-prf-vault.md)。以下のうち該当する項は 004 の時点の記録。

## 状況

帳簿は事業体ごとの SQLite ファイルと registry の DB に分かれている。Mac の故障や紛失に備え、別の場所へ定期的に写しを取りたい。写しは帳簿の全データを含むので、置き場所（外付けのドライブやクラウドの同期フォルダ）が漏れても読めないようにする。依存は増やしたくない（Constitution VII）。

## 決定

- **形式**: 1 つのファイル（`.tbk`）。ヘッダー（平文の JSON: 形式の版、アプリの版、Mac の ID、作成日時、鍵の導出の parameters、nonce）と、暗号化した本体（JSON のマニフェストと各 SQLite の写しの連結）から成る。鍵は Argon2id（`crypto.argon2`、memory 65536 KiB、passes 3、parallelism 1、salt 16 バイト）で 32 バイト。暗号は AES-256-GCM で、ヘッダー全体を AAD にする。途中で切れた・1 バイト書き換えた・パスフレーズが違うファイルは、タグの検証で落ちる。復号はタグの検証が通るまで平文を使わない
- **スナップショット**: 各 DB に `VACUUM INTO` を実行して写しを作る（書き込みを止めず、一時点の一貫した内容になる）。registry の写しは、削除禁止のトリガーを控えて外し、認証・設定・実行記録の表の全行を消し、トリガーを作り直して `VACUUM` する。`app_settings`（Mac の ID、置き場所など端末に結びつく設定）と `backup_runs` もバックアップに含めない。平文の写しは `.tmp/` の下に作り、`finally` で消す。起動時に、前回の異常終了で残ったものを消す
- **自動の判断**: server の起動中、1 時間ごとに確かめる。最後の確認（成功または変更なし）から 24 時間以上たっていれば、スナップショットの内容の SHA-256 を前回の成功と比べる。**「変更なし」にするのは、内容が同じで、置き場所に前回のファイルがあり、パスフレーズを変えていないときだけ**。1 つでも欠ければ書く。手動の実行と、設定の保存・パスフレーズ変更の直後の実行は、変更なしにしない。最後の確認から 48 時間、直近の失敗、パスフレーズが使えないときは画面の上部に知らせる
- **書き込みと世代**: 置き場所に `.partial` で書き、`fsync` して読み戻し、復号と検証が通ってから最終の名前に改名する。成功の後に、この Mac のファイルだけを世代の規則（直近 30 日は日ごとに最新の 1 つ、それより前は月ごとに最新の 1 つ、7 年より古いものは消す）で整理する。選び方は domain の純関数
- **パスフレーズ**は Mac のキーチェーンに保存する。`/usr/bin/security -i` の標準入力に 1 行を流す（引数に載せると `ps` に出る。`-w` を最後に置いて標準入力から渡す方法は、実機で使えないと確かめた）。パスフレーズは 12 文字以上で、改行を含められない。失うと復元できないことへの同意を設定で求める
- **版**: アプリの版（registry と tenant のマイグレーションの適用数）が今のアプリと完全に一致するバックアップだけを受け付ける。新しくても古くても拒否する
- **復元は server を止めて行うコマンド**（`pnpm restore -- --file <.tbk>`）。復号と検証、版の確認、要約の表示、今の帳簿のバックアップ（復元の前の写し）、展開、`integrity_check`、元の `app_settings` の引き継ぎ、元のデータ場所の `.before-restore-<日時>` への改名、の順。画面からは、ファイルとパスフレーズで中身を検査するところまでを行う

## 理由

- 依存なしで、機密と改ざんの検知の両方が得られる（Node 組み込みの `crypto`）。帳簿は数 MB〜数十 MB の想定なので、ファイル全体をメモリで扱う
- `VACUUM INTO` は、別の接続の書き込みでやり直しにならない（`db.backup()` はやり直しがある）
- 変更の検知のために、帳簿の書き込みの経路に手を入れずに済む。「変更なし」の条件を厳しくして、置き場所のファイルが消えたときとパスフレーズが変わったときに、最新の内容を必ず置く
- 端末に結びつく設定と認証の情報は、別の Mac に持ち込むと意味がなく、漏れたときの害もある
- 動いている server の DB を差し替えると、開いた接続の扱いが複雑になる。新しい Mac ではパスキーがなく画面に入れないので、画面に頼らない復元の経路が要る
- 開発中で帳簿の形式を更新しないので、版の完全一致だけで足りる

## 検討した代替案

- チャンクごとの GCM（ストリーム）: 帳簿の大きさでは不要
- tar・zip の依存: 自前の単純なアーカイブで足りる
- 画面から復元する: 動いている DB の差し替えが要り、新しい Mac では画面に入れない
- 版の新旧を比べて古いものを移行する: 開発中は旧版との互換を考えない

## 影響

- 暗号化・形式・復元は `packages/db/src/backup/` に閉じる。世代の選び方と自動の判断は `packages/domain/src/backup/` の純関数
- 復元した帳簿には認証の行がなく、次の起動でパスキーの登録から始まる（[ADR 0006](0006-passkey-sessions.md)）。バックアップの置き場所は設定し直す
- 復元のコマンドは、server の実行の関数を使わず、db の部品だけで復元の前の写しを書く。`backup_runs` には記録しない
- `.gitignore` に `*.tbk`、`data.restore-*/`、`data.before-restore-*/` を足す
- 性能は `pnpm bench:backup`（SC-005）で確かめる
