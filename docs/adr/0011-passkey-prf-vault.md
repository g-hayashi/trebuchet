# ADR 0011: パスキーの PRF でデータ鍵を包み、DB 全体を暗号化する

- 状態: 採用（注記: 影響の `pnpm verify:freee --continue` は、フラグ（`--continue`・`--keep`）ごと削除した。今の `pnpm verify:freee` にはない）
- 日付: 2026-10-30
- 関連: specs/008-passkey-vault/design.md（D1〜D12）、[ADR 0001](0001-sqlite-driver.md)（ドライバー）、[ADR 0006](0006-passkey-sessions.md)（回復コード・セッションの節を置き換える）、[ADR 0007](0007-backup-format.md)（パスフレーズ・キーチェーンの節を置き換える）

## 状況

帳簿の DB（registry と事業体ごとの SQLite）は平文でディスクにあり、守っているのはサーバーの認証だけだった。ファイルを直接読まれる（盗難、バックアップ先の漏れ、他のプロセス）と中身が見える。かといって、DB の鍵をキーチェーン・環境変数・ファイルに平文で置くと、鍵の置き場所が新しい弱点になる。利用者は本人 1 人で、Mac の Touch ID が使える。パスキーを失ったときに、帳簿を取り戻す手段も要る。004 では、回復コードをサーバーが確かめ、バックアップのパスフレーズをキーチェーンに置いていた。

## 決定

- **データ鍵（DK）**: 32 バイトの乱数。初回の設定で 1 回だけ作り、以後は変えない（包み直すだけ）。DK はディスクに平文で置かない。サーバーのメモリーにだけ置き、施錠で 0 で埋める
- **DB の鍵**: `HKDF-SHA256(DK, info)`。info は registry が `trebuchet/db/registry/v1`、事業体が `trebuchet/db/tenant:<entityId 小文字>/v1`。registry と事業体の DB は、この鍵で SQLCipher 方式（`PRAGMA cipher='sqlcipher'`、`PRAGMA key`）で暗号化する。ドライバーは `better-sqlite3-multiple-ciphers`（[ADR 0001](0001-sqlite-driver.md)）。鍵が違えば `SQLITE_NOTADB` を例外として上げ、空の DB として扱わない
- **DK の包み**: KEK = `HKDF-SHA256(ikm, salt=wrap.salt, info=trebuchet/dk-wrap/v1)`、包みは `AES-256-GCM(KEK, iv, DK)`、AAD は種類（`passkey`・`recovery`）と資格情報 ID。包みが開けること（GCM の検証）が、正しさの判定のすべて
  - **パスキー**: ikm は WebAuthn の PRF 拡張の出力。入力は資格情報ごとに保存する 32 バイトの乱数 `prf_salt`。パスキーごとに包みを 1 行持つ。PRF が使えない認証器は 400 `PRF_UNSUPPORTED` で拒否する
  - **回復キー**: ikm は 160 ビットの乱数そのもの（Crockford base32、4 文字区切り）。包みは常に 1 行。キーそのもの・ハッシュは保存しない。作成と再発行の応答で 1 回だけ表示する。Argon2 は使わない（入力が十分なエントロピーを持つため）
- **`data/auth.sqlite`（平文）**: `passkeys`（`prf_salt` を含む）、`key_wraps`、`sessions`（トークンのハッシュ）、`auth_events`。秘密を持たない（公開鍵、PRF の入力、包んだ DK、ハッシュ、操作の記録）。registry の認証の表はここへ移し、`recovery_codes` と `hashToken` による回復コードの照合はやめた。トークンのハッシュ（`hashToken`）はセッションにだけ使う
- **施錠と解錠**: サーバーは起動時に `auth.sqlite` だけを開く。パスキーの認証（PRF の出力で包みを開く）か回復キーで DK が得られると解錠し、registry と事業体を開く。施錠中の帳簿の API は 401 `LOCKED`。サインアウトで全セッションを消して施錠する。セッションは無操作 30 分で失効し、有効なセッションが 1 つもなくなると施錠する。起動時・施錠時に `sessions` を全部消す（DK が消えるので、残ったセッションは使えない）
- **初回の設定**: パスキーの登録 → PRF の出力を得るための認証 1 回 → DK と回復キーを作り包みを 2 行 → registry と事業体を空から作る。以前の registry・事業体は `data/discarded-<時刻>/` に移す（消さない）
- **回復**: 回復キーで解錠すると、10 分の回復のセッションを出す（できるのは新しいパスキーの登録だけ）。登録に成功したら、新しい回復キーで包みを差し替えて 1 回だけ表示し、全権のセッションに上げる。試行の失敗ごとに 1 秒待たせ、全体のロックはしない（回復キーは 160 ビットの乱数で、総当たりは成り立たない。ロックは正規の利用者を締め出すだけ）
- **パスキーの追加・削除、回復キーの再発行**は、全権のセッションに加え、直近 5 分以内のパスキーの再認証を要求する（403 `REAUTH_REQUIRED`、`POST /auth/reauth/options`・`verify`）。最後の 1 本のパスキーは削除できない。パスキーの削除と同じトランザクションで、その包みも消す
- **バックアップ**: 鍵は `HKDF-SHA256(DK, salt=ヘッダーの salt, info=trebuchet/backup/v1)`。ヘッダーに、取った時点の recovery の包みを入れる。復号は、今の DK（解錠中）か、回復キーで開いた包みの DK で行う。AES-256-GCM でヘッダー全体を AAD にするのは 0007 のまま。中の写しは平文の SQLite（外側の AES-GCM が守る。`VACUUM INTO` は暗号化した DB の写しも同じ鍵で暗号化するため、平文の写しを取るにはいったん鍵を外す）。`auth.sqlite` は含めない
- **復元（`pnpm restore`）**: 回復キーを標準入力から読む。ヘッダーの包み → 今のデータ場所の `auth.sqlite` の recovery の包み、の順に試す（DK は変わらないので、回復キーを再発行した後でも古いバックアップを戻せる）。復元の後は `auth.sqlite` を recovery の包みだけで作り直す。次の起動で回復キーで解錠し、パスキーを登録する
- **背景の処理**（バックアップの定期実行、定期仕訳の自動登録）は、解錠中だけ動かす
- 公開の手続きの一覧（`requiresAuth`）と、Host → CSRF → 認証の順は 0006 のまま。認証を無効にする設定・環境変数を作らない

## 理由

- DB の鍵を平文で置く場所がなくなる。鍵の素材（PRF の出力）は認証器の中にあり、サーバーは認証のたびにしか得られない。サーバーのプロセスが止まれば鍵は消える
- DK を包んで保存すれば、パスキーの追加・削除や回復キーの再発行は包みの出し入れだけで済み、DB の再暗号化は要らない
- 包みの検証だけを正しさの判定にすれば、回復キーのハッシュを保存しなくて済む（ハッシュは総当たりの手がかりになる）
- 回復キーが 160 ビットの乱数なら、鍵の強化（Argon2）を使わずに足りる。パスフレーズより忘れ・弱さの問題が小さい
- バックアップの鍵を DK から作れば、利用者が覚える・保管するものは回復キー 1 つに集まる。ヘッダーに包みを入れるので、新しい Mac でも回復キーだけで戻せる
- 暗号化は DB の層にあるので、リポジトリ・ドメイン・画面の業務ルールは変わらない

## 検討した代替案

- DB の鍵をキーチェーンに置く: 鍵が平文で端末にあり、同じ端末のプロセスが読める。パスキーを使う意味が薄い
- パスキーの署名だけで認証し、DB は平文のまま（004 の方式）: ファイルを読まれたら終わる
- パスワードから鍵を作る（Argon2id など）: 弱いパスワードと保管の負担が生じる。パスキーの PRF のほうが強く、手間も少ない
- 回復キーのハッシュを保存して照合する（004 の回復コード）: DB が見える相手に総当たりの手がかりを渡す。包みの検証で足りる
- 回復キーの失敗で全体をロックする: 正規の利用者を締め出す。失敗ごとの 1 秒の待ちで足りる
- 既存データの移行: 開発中で利用者がいないので作らない（前のデータは `discarded-<時刻>/` に移す）

## 影響

- ドライバーが `better-sqlite3` から `better-sqlite3-multiple-ciphers` 13.0.3 に変わった。同梱のビルド済みバイナリで動き、ビルドは要らない
- 鍵の計算（`vault-crypto.ts`、`recovery-key.ts`）は `packages/db/src/` にある（復元のコマンドが使うため）。`packages/domain` は `node:crypto` を使えないので、domain には置かない。server は `lib/vault.ts`（解錠の状態）、`session-sweeper.ts`、`reauth.ts`
- テストは `useTempDataDir`（固定のテスト用 DK を入れる）を使う。E2E は仮想の認証器に `hasPrf: true` を付け、回復キーを引き継ぐ `enterVault` で解錠する。パスキーの書き出し・戻しは PRF を失うので使わない
- `pnpm verify:freee --continue` は使えない（実行ごとに乱数の DK を作るため。利用者の判断でそのままにする）
- パスフレーズ・キーチェーンのバックアップの経路は消えた。`SecretStore`（キーチェーン）は 006 の外部の AI の API キーのために残る
- 回復キーを失い、すべてのパスキーも失うと、帳簿は読めない。回復の手段はない（利用者への説明は画面と README）
- 不変条件 INV-51〜54（`specs/INVARIANTS.md`、正本は design.md D10）
